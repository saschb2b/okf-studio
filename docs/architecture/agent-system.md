# Decision

One [Agent Panel](../features/agent-panel.md) hosts two boundaries. The first runs external agent processes over Agent Client Protocol (ACP). The second runs a native Studio Agent on API or local model providers.

Delegating bundle-sized work across several bounded runs is a separate decision: see [Agent Orchestration](agent-orchestration.md).

# Why this decision exists

Studio needs provider choice without duplicating bundle access, permissions, staging, and session behavior for every agent. Separate vendor integrations would drift into different security rules and make OKF specialization depend on one model or subscription. A browser-owned integration would also place process, credential, network, and filesystem authority in the wrong layer.

One Rust host keeps those authorities consistent while ACP and the native provider remain replaceable execution paths. The shared capability, context, artifact, and reviewed-write contracts make OKF behavior a Studio property. Provider-specific limits stay visible without changing which layer decides access or whether Studio may apply a proposed revision.

# Granted bundle library and federation

## Why federation exists

Many OKF tasks need evidence from related bundles: comparing definitions, finding a shared source, or planning a migration into one active bundle. Without a Studio-owned federation path, the user must copy that material into the destination. The other option is to give an agent several filesystem roots and rely on prompt instructions to keep writes separate.

The granted library reuses folders the user has already authorized and gives every result a stable bundle identity. Federation remains read-only evidence, and the active bundle remains the only staging destination. This supports cross-bundle reasoning without merging namespaces, duplicating knowledge, or widening the agent's filesystem authority.

Rust owns a separate bounded library of bundles that the user previously granted. Each record has an opaque UUID, internal canonical root and scope root, title, kind, and counts. It also holds type and tag summaries, the last observed revision fingerprint, and the last-seen time. The UUID survives rescans and restarts. Paths stay inside Rust and never serve as cross-bundle identity. Rust derives the active marker only after the current root passes the ordinary bundle authorization boundary.

Federated commands accept at most eight distinct UUID and expected-revision pairs. Before every query, Rust rechecks the remembered grant, canonical folder, detected bundle root, and revision fingerprint. Rust reads available results fresh. Missing, revoked, and changed selections return a per-bundle partial status without stale concept results. Rust caps inventory, search, type, tag, source-reference, and relationship-candidate queries. Inventory interleaves selected bundles, so a large first bundle cannot consume the complete bounded page.

Every concept result carries bundle UUID, bundle title, concept ID, revision fingerprint, and grant state. Source rows carry the same identity tuple. Relationship candidates preserve the identity of both concepts. Rust limits them to matching-title or shared-source evidence with `requiresReview` set. Titles and paths never merge namespaces.

The frontend converts an exact user-reviewed selection into bounded Markdown evidence for the curated task. It treats bundle text as untrusted data and exposes the sources in the composer. The active connection and staged tree remain bound to one canonical active root, so other bundles cannot receive writes through federation. Federation adds evidence, not another filesystem or MCP primitive.

# Boundaries

ACP standardizes capability negotiation, agent-owned auth, sessions, streaming, tools, permission requests, diffs, filesystem requests, cancellation, and optional restore. It avoids separate Claude and Codex clients. Rust keeps one canonical bundle-root representation from folder grant through agent connection and ACP session dispatch. On Windows it removes the verbatim prefix before storing or sending the root. Bundle comparisons treat the ordinary `C:\...` and equivalent `\\?\C:\...` forms as the same canonical directory. This preserves exact bundle scoping while accepting connections created before Studio introduced the normalized representation.

ACP does not replace an external agent's system prompt. The native Studio Agent guarantees the packaged [OKF capability resources](../../.agents/skills/okf/capabilities.json), system prompt, scoped tools, validation, and staged writes. External agents receive bundle cwd, explicit resources, client permissions, and Studio OKF tools over MCP where supported. The MCP server exposes the complete active capability catalog and a closed resource loader. Generic ACP chat can therefore choose the same methods as a named task. Studio labels capability material as client context and never claims it changed the external agent's system instructions.

## Why capabilities are narrow

One large OKF instruction bundle would make every task pay for methods and examples it does not need. Some methods also conflict when applied together: inspect is read-only, revision forbids semantic changes, enrichment permits sourced additions, and repair requires a reproducible defect. Provider-specific prompts would recreate the same drift across agents.

The shared kernel holds format rules, the compact router, and invariant safety guidance. Narrow capabilities add only the method, tools, artifact kinds, and completion checks needed now. Named tasks select a deterministic route before send. Generic chat sees every active capability but loads one method on demand. Studio can inspect and benchmark each method independently, while every provider receives the same declared contract through its supported delivery path.

The packaged catalog keeps invariant trust rules in the native boundary and task method in versioned resources. `okf-core` owns the compact router, shared specification, command reference, templates, writing contract, and changelog. Ten narrow capabilities own inspect, create, enrich, audit, repair, cited research, change impact, migration, concept authoring, and meaning-preserving revision methods. Each declares one risk class, exact tool set, artifact kinds, and required inputs. Each also declares an ordered method, stop conditions, completion checks, and worked and adversarial examples. The benchmark gate requires one task contract per narrow capability and rejects tool or artifact drift.

Removing a capability removes it from generic discovery and its task entry point without changing the native safety boundary. Settings exposes metadata and digests, never resource bodies or an enablement claim. Guided task selection crosses IPC as a stable task ID plus an accepted bounded context manifest. Rust rejects unknown IDs, oversized manifests, task mismatches, and capability routes that differ from the curated task table. The host then attaches the selected narrow instruction resources in addition to the shared kernel. It records them in the turn receipt.

Capability artifact contracts use one `okf-artifact` envelope documented in the shared templates. Before trusted rendering, Rust validates the schema, closed artifact and status kinds, and the exact current bundle fingerprint. It also validates revision ancestry, identifiers, field and item bounds, bundle-relative concept paths, source references, and citations. The webview receives typed structure only after that check. It retains invalid output as transcript prose and keeps local planning edits unsent. It rejects older continuations and routes any Markdown export through the existing reviewed stage. The resulting [Structured Agent Work](../features/structured-agent-work.md) is presentation over the same security boundary, not a new write path.

Studio advertises ACP v1 session configuration support for select and boolean options. New and loaded session responses cross Rust as a complete ordered snapshot after reduction. Rust accepts at most 64 options, 64 groups per selector, and 512 values per selector. IDs, names, descriptions, categories, group labels, and value labels must be non-empty where required, control-safe, and capped at 512 characters. Duplicate option and value IDs keep their first occurrence.

Rust omits a select when its confirmed current value is absent from the accepted values. It also omits a future unknown option kind without hiding other usable options. Unknown semantic categories lose only their category when unsafe. They do not change provider behavior.

After saved-work discovery resolves, the frontend prepares one draft session for a fresh thread so the agent's choices can appear before its first prompt. Resume adopts the loaded session and its own snapshot instead. A connection, bundle, or thread change invalidates an in-flight draft or configuration response.

The connection actor retains one confirmed option snapshot per session. `session/set_config_option` accepts only an advertised option, matching value type, and advertised select value. Actor serialization prevents overlapping changes on one connection. Every successful response replaces the full snapshot, including options added or removed as a consequence of another selection. An agent-owned `config_option_update` also replaces the full session snapshot and emits a separate session event even when no turn is active. The webview never invents Claude, Codex, or local-provider model names and cannot send an arbitrary hidden option through forged IPC.

# Security and credentials

External agents own credentials. Studio invokes ACP-advertised methods and does not persist subscription secrets. Studio Agent API keys live in Windows Credential Manager, macOS Keychain Services, or the desktop's Secret Service on Linux. Settings retain only provider metadata and a credential-present marker. The uncontrolled password field clears with the setup form. After entry, secrets remain in Rust. Rust zeroes them when transient values drop, keeps them out of diagnostics and response bodies, and never returns them to the webview.

Opening remains read-only. Client filesystem methods canonicalize paths and reject traversal, symlink escape, access outside granted roots, and built-in sensitive-path classes. Studio writes target a staged tree, validate, then apply atomically after review.

Bundle creation starts with a separate proposal boundary. Create and Enhance responses may include one fenced `okf-proposal` JSON object. That object carries bounded concept metadata, proposed Markdown links, and index membership. The webview parser selects the newest block, validates counts and bundle-relative path shapes, and renders structured display metadata beside the transcript. It does not accept file bodies or call the Rust staging commands. Only the newest valid proposal can expose a generation action, and only inside a marked Create or Enhance workflow.

After the user grants interactive writes and activates that action, Studio first asks Rust to select `create` or `enhance` mode on an empty staged tree. Studio then records an ordinary follow-up that asks the connected agent to create the reviewed structure through the mediated staged-write channel. Create mode treats every path as new and validates an empty mirror containing only selected draft files. It cannot apply to the active bundle or expose its checkpoint. After zero-error validation, Rust accepts a portable single-component folder name and a parent selected through the native picker. It rejects active-bundle descendants and every existing destination entry.

Rust writes the selected revision into a private sibling directory, syncs each file, and renames the complete directory into place. Cancellation returns no path. Success returns only the folder name and count.

Enhance mode uses the ordinary bundle overlay and Restore, but records an explicit reviewed set beside the rejected-hunk set. Validation and Apply require every complete modified-file diff hunk to appear in that reviewed set at the current diff revision. New files do not carry this overwrite guard. Rust rejects a mode change while any staged file remains.

An external process may bypass client filesystem methods. Client checks do not sandbox it. Standard external connections therefore remain interactive and carry a containment warning.

The write-grant IPC requires a closed `interactive` or `unattended` mode. Rust accepts `unattended` only when the live connection carries launcher-produced evidence for a verified Linux Bubblewrap or Windows AppContainer Restricted offline profile. The grant lasts 30 minutes and can only stage changes. Its Rust-owned deadline, an explicit revocation, disconnect, application exit, or host failure ends it. A forged webview request, saved launch preference, or stale preflight cannot weaken that boundary.

Enforcement state must originate in the process launcher after the platform restriction is active. A saved wrapper command, profile label, agent capability, or provider-owned sandbox claim is not sufficient evidence.

A qualifying host profile reports its readable mounts, writable roots, network policy, credential exposure, process lifetime, and stop conditions. It must protect Git metadata and credential paths even when they appear below an otherwise writable mount. Windows combines AppContainer filesystem and network isolation with a Job Object that owns process lifetime. Studio never calls the Job Object alone a sandbox. Any platform without a verified host remains interactive, and a failed verification or lost owner returns the connection to deny.

The catalog runs a separate Rust-owned confinement-backend preflight without starting an agent. On Linux it searches absolute `PATH` entries for a canonical system Bubblewrap binary. That binary must be a regular root-owned file, non-setuid, and free of Linux file capabilities. It must also be neither group- nor world-writable, and readable and executable by ordinary users.

The three-second probe clears the environment. It then asks that exact binary to create read-only root, user, network, IPC, PID, and UTS namespaces. The same call must prevent nested user namespaces, start a new session, apply parent-death handling, and execute its own `--version` inside the namespace. All standard streams point to the null device. On Windows the preflight creates an AppContainer with no capabilities, resolves its private profile folder, and deletes it. Missing, rejected, failed, and unsupported states are closed values.

macOS remains unsupported until Studio implements and tests a Seatbelt policy. Preflight is diagnostic input, never launcher evidence, and by itself cannot permit unattended work.

The Linux launcher has a live Restricted offline branch. Its Bubblewrap plan starts from an empty mount namespace. It mounts only selected system runtime files, exact declared agent roots, and the Rust-granted bundle as read-only. The launcher refuses a bundle or agent root under `/tmp`, `/run`, `/proc`, or `/dev` before launch. The profile mounts private filesystems over those paths after the read-only binds. Such a mount would otherwise silently shadow the grant and hand the agent an empty directory in its place.

Managed catalog commands get their dormant app roots from the verified Node receipt and canonical installed package root. They do not infer or expose their common app-cache parent. A restricted custom command contributes only its canonical executable as an agent root. The plan supplies private `/tmp` and `/run` plus fresh `/proc` and `/dev`. It hides every protected Git, credential, secret, and packaged-agent path found below the bundle. It also rejects an executable outside the visible mounts, caps the policy walk, disables nested user namespaces, and isolates networking.

The launcher repeats trusted-backend discovery and the namespace probe before every restricted start. A failed check returns an error and cannot fall back to Standard.

A dedicated Ubuntu 24.04 CI job installs the distribution Bubblewrap package and runs the real branch. The policy's nested-user-namespace denial needs Bubblewrap 0.8 or newer, which rules out the 22.04 image's 0.6.1. The job also re-enables unprivileged user namespaces where the image's AppArmor gate would deny the probe. Its shell fixture proves visible bundle reads, protected-file masking, rejected bundle writes, private temporary storage, and process completion.

The catalog exposes Restricted offline only when that backend is ready, and only saved custom ACP commands can select it. Standard remains the default. Managed Claude Agent and Codex profiles stay off the branch. They return only when Studio can support their network authentication and persistent credential state without broadening the mount policy.

The native Windows branch uses [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), a Windows security boundary independent of the process-lifetime Job Object. The outer helper is Studio's own executable and receives only the ACP stdio handles plus the custom profile's allowlisted environment. It canonicalizes one self-contained `.exe` and creates a unique AppContainer with no capability SIDs. It then copies the executable into that container's private profile and launches it with an explicit three-handle inheritance list. The bundle receives no AppContainer filesystem grant. Reads and staged writes therefore stay behind Studio's bounded ACP methods, while the operating system denies ordinary bundle, Git, credential, and network access.

The helper and child remain in the launcher's kill-on-close Job Object. A recovery ledger contains only the profile identity and helper PID. Preflight removes stale profiles only after the recorded process has stopped. A native Windows fixture launches the Rust test binary through the real branch. It verifies that the token is AppContainer, that a host sentinel is unreadable, and that private scratch remains writable.

Permission precedence is: non-overridable security rules, deny, confirm, allow, thread grant, tool default, global default. Writes outside roots, Git metadata, credentials, and packaged instructions are built-in denials.

# Installation, persistence, and network

Registry membership is not a sandbox. Studio shows publisher, repository, license, exact version, distribution, and runtime before install. Binary archives require verified digests. `npx` agents use an isolated app-managed Node runtime/cache. Installation never starts the agent.

The first catalog is a versioned JSON manifest bundled into both builds from one source file. React reads it through a generic IPC function. The desktop command parses it into Rust structs before returning it. Browser development uses the same manifest directly. Catalog data holds provider names, authentication methods, runtime kind, package coordinates, pinned versions, and optional repository and website links. None of it becomes brand-specific UI or a process branch. Updating the bundled snapshot is explicit and reviewable. A later remote refresh must verify a signed or pinned registry response before replacing it.

The 2026-07-14 snapshot mirrors the upstream ACP Registry's npm distributions: Auggie CLI, Claude Agent, Cline, Codex, Factory Droid, Gemini CLI, GitHub Copilot, and Qwen Code. Each entry carries its verified tarball size and SHA-512 value, measured from the published archive. A distribution may declare bounded `environmentDefaults` (pinned name/value pairs appended after the host passthrough, so they win on conflict). Studio uses them to disable Auggie's and Factory Droid's self-update paths, which would otherwise replace the verified install at runtime. Cline, Factory Droid, and GitHub Copilot use loader shims that resolve platform packages at run time. Studio checked each shim under its script-free dependency installation before pinning it.

Cursor is the first `binary` distribution, with six per-platform archives pinned by size and by SHA-256 value. Studio measured those values from the published archives at snapshot time, because the upstream registry entry carries no checksum. Its launch skips the publisher's `cursor-agent` shell and PowerShell launchers entirely.

Studio spawns the archive's bundled Node executable with the pinned `index.js` path and `acp` argument directly. It sets the shim's `CURSOR_INVOKED_AS` value through the ordinary environment defaults. Goose, Kimi CLI, and OpenCode remain planned entries, because they publish neither an npm package nor a checksummable stable archive layout Studio has verified. Studio installs nothing it cannot pin and verify.

Custom ACP profiles are separate user data. Rust validates and stores a display name, absolute executable path, argv array, and an allowlist of environment variable names in the app-data directory. It rejects relative paths, shell strings in the executable field, environment assignments, invalid variable names, and oversized fields. IPC does not accept environment values, and Studio does not persist them. The ACP host inherits only the named variables when it starts the executable directly, without a shell.

Studio-model profiles are separate bounded metadata under the same Rust-owned app-data directory. A profile contains an opaque ID, display name, closed provider kind, normalized HTTP or HTTPS base URL, and a credential-present marker. Rust revalidates every stored record and permits at most 32 profiles. It rejects URL credentials, queries, fragments, duplicates, and files above 128 KiB. No API key, prompt, bundle path, model response, test result, selected model, or transcript enters this file.

The profile ID addresses a separate OS credential entry under the compatibility service name `app.okfviewer.desktop`. Saving writes the credential before metadata, and attempts to remove it if the metadata write fails. Removal deletes the credential first and treats an already-missing entry as success. A missing or locked credential service fails explicitly without falling back to plaintext storage.

An explicit connection test sends one Rust-owned `GET` with environment proxies and redirects disabled. It applies five-second connection and ten-second read limits and a 256 KiB response cap. It reads Ollama `/api/tags` or an OpenAI-compatible `/v1/models`. It retains at most 256 unique control-free model IDs of at most 256 characters, and returns only that bounded list and normalized endpoint metadata to the webview. Studio supports API keys only for custom OpenAI-compatible profiles. They travel as bearer credentials over HTTPS or to a literal loopback host.

A native Studio Agent connection enters the same app-owned worker registry, bundle-scoped session command surface, turn event reducer, staged-change service, and disconnect lifecycle as ACP. It does not pretend to speak ACP. Connect repeats the model-list probe in Rust and accepts only a selected bounded ID still advertised by the saved profile. A credentialed profile retrieves its key directly from the OS store for that probe and each model request.

A worker keeps at most 32 recent user and assistant messages and 256 KiB of retained text in memory. It posts non-streaming JSON to Ollama `/api/chat` or the compatible `/v1/chat/completions`, and accepts at most 1 MiB of response JSON. Rust removes response controls, and visible text crosses IPC in chunks of at most 64 KiB characters. Environment proxies and redirects remain disabled. Every 3xx response fails with its HTTP status, and Studio never contacts its destination. Connect, write, and read limits are five, ten, and 120 seconds.

One session has at most one active turn. Cancellation atomically wins against completion, emits one cancelled stop, and suppresses the eventual blocking result. Worker teardown suppresses every late result. Bundle context paths and image sources fail closed. The frontend permits extracted text sources, guided starters, and the ordinary interactive write grant while keeping bundle attachments and images disabled.

Rust prepends one Studio-owned system message to every native provider request without adding it to retained conversation history. The message defines the native input boundary and limits bundle and source claims to advertised tool evidence. It denies arbitrary files and external systems, prohibits credential requests, and treats user, bundle, and source text as untrusted knowledge. Its available-capabilities section comes from the active [declarative OKF capability pack](../features/capability-packs.md), whose typed capability manifest and resources have independent versions. The system message includes only capability ID, version, description, and manifest digest. Detailed resources remain unloaded.

The built-in `okf-foundation@1.2.0` pack binds that catalog to the shared Markdown templates and the `okf-artifact-v1` and `writing-revision-v1` JSON Schemas. It also binds every closed Studio tool ID its skills may require. The build and runtime both verify its built-in provenance, Studio and schema compatibility, conflict list, known compile-time resource paths, media types, and SHA-256 digests. Deny-unknown-field deserialization leaves v1 with no script, hook, binary, installer, environment, or user-defined MCP-command surface. A separate app-data receipt records active or legacy mode and the prior built-in digest. Rollback changes capability routing only. It never rewrites profiles, sessions, checkpoints, settings, credentials, memory, routines, or bundle grants.

Detailed guidance uses progressive disclosure through a closed native tool. The provider receives one `load_okf_capability_resource` function schema with manifest-derived capability and resource ID enums. Before any executor runs, the provider loop rejects a call whose name was absent from the exact tool definitions advertised for that turn. The closed dispatcher separately rejects unknown capabilities, undeclared resources, extra fields, malformed arguments, oversized calls, and excessive rounds. It returns only the selected compile-time resource with its capability version, digest, and stable `okf-studio://` URI. A successful native load emits separate tool-observed evidence. Catalog delivery alone never claims that the model used the resource.

External ACP sessions receive the equivalent progressive boundary through the bundled read-only MCP server. The `okf_capability_catalog` tool returns metadata for every capability in the active pack. The `okf_capability_resource` tool accepts one declared capability and resource ID. It then returns the same compile-time bytes, version, digest, media type, and stable URI that Studio Agent uses. Unknown, inactive, undeclared, or malformed requests fail. Loading guidance adds no bundle, source, network, staging, or write authority.

The same loop advertises ten read-only active-bundle tools. Their argument schemas match the ACP MCP names. Their Rust executor calls the same inventory, read, search, source-reference, traversal, validation, and knowledge-health methods rather than duplicating query logic.

The health engine is a pure `okf-core` analysis over one parsed snapshot. It mirrors validator output only in its conformance category and labels every other finding as a fact or heuristic. It gives every rule an ID, version, severity, evidence, repairability, and suppression fingerprint. Summary, detail, affected-concept, and deterministic-repair tools use progressive disclosure. Detail calls require the summary fingerprint.

Health analysis accepts at most 10,000 concepts and 50,000 intra-bundle links, including unresolved targets. A request above that bound fails without changing tolerant bundle opening. The native provider already runs tool work in its blocking worker. The MCP health path reparses its canonical root for each request and fingerprints the root again after analysis. It discards obsolete output when live reload changes the bundle. The session accepts concept IDs, finding IDs, fingerprints, filters, cursors, and line ranges instead of paths.

Structured output above 96 KiB fails with a bounded request to narrow the query. The executor distinguishes a completed call, a recoverable tool failure, and a fatal host error. A recoverable failure produces a failed lifecycle card and bounded `Studio tool error` result. The model can then correct its call within the existing round limits. Cancellation and host shutdown remain fatal and never return to the model as tool data. The model never receives an arbitrary filesystem primitive.

An accepted local turn with user-attached extracted text adds two ephemeral source tools. Inventory maps the validated inputs to `source-1` through `source-8` and returns only bounded provenance, adapter receipts, warnings, digests, and sizes. Read resolves one of those synthetic IDs in memory, repeats its receipt, and returns a bounded line page of at most 65,536 characters. Unknown IDs and extra arguments fail closed. Only that blocking provider turn captures the source values. They never enter `LocalSession`, and they disappear with the tool definitions when the turn ends. Rust rejects images before acceptance, because native providers do not advertise image support yet.

Four native staging tools expose proposals without exposing Apply. Inventory returns only the current Rust-owned snapshot. Propose accepts an atomic batch of one to 16 complete UTF-8 Markdown files with bundle-relative forward-slash paths. The cap is 64 KiB per file and 192 KiB per call. The local executor joins those reported paths to the canonical session root and hands the batch to `SessionStages`. That service clones the current stage and reuses the ordinary grant, containment, symbolic-link, protected-path, file-count, and byte checks before committing the candidate.

A rejected path leaves the prior stage unchanged. A successful call emits the ordinary staged-change event and a `staged` lifecycle state. No content crosses that event. Diff returns at most 64 KiB of the existing structured unified diff. Validation reduces the existing isolated result to 100 issues, 50 nodes, and 100 edges while retaining totals and truncation state. These read tools cannot record hunk choices.

Rust caps argument objects at 256 KiB before dispatch. Provider responses remain capped at 1 MiB, and the ordinary 96 KiB result limit still bounds the next model message.

The provider module translates Ollama and OpenAI-compatible wire shapes. Only bounded lifecycle metadata crosses to the webview. Tool request and result messages exist only inside that provider turn. Retained history still contains the original user message and final assistant text. The loop grants no arbitrary-file, unrequested network-fetch, hunk-approval, apply, or direct-write capability. Native proposals enter the same reviewed staging boundary as ACP writes and cannot reach disk without the separate human validation and apply flow.

Studio thread metadata uses the existing Tauri store under the compatibility filename `okf-viewer.json`. It keeps at most 50 newest entries and at most one current plus one archived pointer for each bundle and agent profile. Each entry contains a canonical bundle root, agent profile ID, opaque ACP session ID, bounded title, and archive flag. It also carries an integer update timestamp, an optional stable OKF task ID, and an optional accepted context manifest capped at 64 KiB. The manifest records the selected capabilities, tools, network and staging scope, bundle revision fingerprint, selected objects and sources, validation counts, budget, and explicit omissions.

Reads treat store contents as untrusted. They discard invalid types, empty or control-bearing strings, oversized fields, unknown tasks, mismatched manifests, unsafe timestamps, and excess entries. The four legacy workflow markers migrate to their stable task IDs. Older general threads migrate without a task. Saving replaces the matching state slot and removes an older state for the same session. Archiving changes only this pointer and clears frontend memory. It does not send ACP `session/close` or claim that ACP persisted a transcript.

Transcript content, prompts, source bodies, tool and plan records, permissions, credentials, usage, and diagnostics remain excluded. The browser development mock uses the same validation and a namespaced local-storage key.

The same store file carries a separate versioned [workspace-memory](../features/workspace-memory.md) envelope. Its closed, body-free item schema and per-kind caps keep preferences, finding fingerprints, task records, and routine definitions distinct from thread restoration. Reads validate bounds, ownership/origin combinations, retention, timestamps, and required per-kind identity. Rust removes invalid, expired, and excess records without blocking bundle load. A bounded quarantine receipt records only detection time and rejected count. Context preferences attach only when bundle root, task, and deterministic fingerprint still match. Deleting memory never touches thread metadata or bundle state.

[Local routines](../features/local-routines.md) use a separate Rust-owned definition file and run ledger in the application-data directory. Rust accepts only schema-v1 deterministic health and bundle-source fingerprint tasks. It canonicalizes the saved bundle through the existing grant, baselines bundle-relative source digests, and hard-rejects agent, model, tool, network, or staging authority. It re-authorizes the bundle and source boundary for every execution.

Rust persists an in-progress receipt before work. A receipt left active by application exit becomes an interrupted failure on load. Runs serialize per bundle and routine, and scheduled catch-up is an explicit saved choice. Rust caps definitions at 32, and the ledger retains at most 512 bounded receipts. The frontend only polls due work while a granted active bundle exists. No background service, external routine process, Apply path, or success inference from missing state exists.

Package installation is a Rust-owned transaction. The bundled catalog pins the npm tarball URL, compressed byte count, unpacked byte count, and SHA-512 Subresource Integrity value. It also pins the package-relative entry point, argv, provider environment names, and any pinned launch-environment defaults. An explicit install request streams into an app-cache staging file with timeouts, a 64 MB hard cap, progress events, and cancellation checks. Studio rejects a size or digest mismatch, archive links, unsupported entry kinds, and every path outside the npm `package/` root. It extracts into a staging directory and renames that directory into its versioned destination only after verification.

The root adapter tarballs do not contain their production dependencies. Studio therefore invokes the pinned runtime's `npm-cli.js` directly through managed Node, inside the staging package. Scripts, audit, funding, and development dependencies stay disabled. On Windows, Studio converts the canonicalized npm entry script back to its Win32 drive form before it becomes managed Node's argv. Node 24 fails to resolve a verbatim `\\?\` main module. The npm process receives a cleared environment, restored only with bounded platform, locale, proxy, and certificate variables. `NODE_OPTIONS` and arbitrary npm configuration cannot inject code or replace the registry.

Bounded installation diagnostics redact inherited values. Dependency installation shares the cancellation token and has a ten-minute deadline. npm verifies registry integrity metadata and writes a package lock. The receipt records the root package integrity plus SHA-256 values for that lock and the launch entry point. Repeated requests require the matching receipt, lock, entry point, and dependency directory.

Studio treats a malformed receipt, or one from an older schema, as stale. It replaces that receipt through the normal verified installation flow instead of blocking preflight. No package lifecycle script runs, and installation does not start the agent.

Studio uses no system Node fallback for catalog agents. The manifest pins the managed runtime to Node `v24.18.0` and records the official nodejs.org archive URL, SHA-256 value, byte count, archive kind, and root directory for Windows x64, Linux x64/ARM64, and macOS x64/ARM64. A preflight command selects only the compiled OS/architecture pair, rejects unsupported targets before network access, checks existing package/runtime receipts, and returns the exact remaining pinned-archive footprint. The UI identifies npm-resolved production dependencies as an additional download whose platform-specific size is determined during installation.

An install first ensures the managed runtime, then installs the ACP package with the same cancellation token. The runtime archive is streamed to a staging file, checked against its pinned size and SHA-256 value, and limited to 128 MB compressed and 512 MB expanded. ZIP and tar paths must remain under the pinned root. Unix Node archives may contain relative `npm` and `npx` symbolic links; Studio permits one only when its normalized target stays inside that root. Absolute or escaping links, hard links, and unsupported entry kinds fail the transaction. The verified runtime directory is renamed into its versioned cache location and recorded before package installation begins.

Binary installation is a parallel Rust-owned transaction with its own caps. The pinned per-platform archive streams to a staging file with a 256 MB compressed limit, must match its exact byte count and Studio-measured SHA-256, and extracts under one expected root directory with a 1 GB expansion cap bounded further by the pinned unpacked size. Links and unsupported entry kinds fail the transaction, the declared executable and launch files must exist before the staging directory renames into place, and no dependency resolution or lifecycle script runs — the archive is complete by definition. The receipt records the archive digest and a SHA-256 over the launch entry file; connect revalidates both and joins each pinned launch-file path to the canonical install root before it becomes argv, converted to Win32 form on Windows.

The React catalog calls preflight before enabling installation. It presents the runtime version and separate runtime/package byte counts — or, for a binary distribution, the single archive size with a note that it bundles its own runtime — subscribes to progress only for the selected install ID, and exposes cancellation without treating a partial transaction as installed. An install receipt changes the catalog state to **Installed**, not **Connected**; no process launch is part of this command. Preflight results are owned by the catalog view rather than each row, so the same state drives the row, the install-state filter, and the panel's connect popover without repeated hashing.

Uninstall is a separate typed command. It refuses while an installation job for that agent is running or while any live connection was launched from its catalog profile, then removes every cached version directory for the agent ID. The managed Node runtime is shared and stays in place. Removal never touches a bundle, and the next preflight simply reports the entry as installable again.

Catalog connection is a separate typed command. Rust revalidates the runtime receipt paths, package receipt, dependency lock, and entry-point digest, then canonicalizes the entry point under the versioned package root. On Windows, the verified `\\?\` path is converted back to the equivalent Win32 drive or UNC form before it becomes managed Node's explicit argv; Node 24 does not resolve a verbatim drive path as its main module. Studio never invokes a shell, `npx`, a package bin shim, or system Node. The child receives a bounded cross-platform process environment plus only the provider variable names declared by the catalog, followed by the catalog's pinned environment defaults, which override a same-named host value; every inherited value joins the existing diagnostic redaction set. A launch failure exposes the exit status and one bounded diagnostic line, without SDK serialization metadata or a runtime stack. Catalog identity uses the same one-active-connection rule and ACP actor as a custom profile, so initialization, authentication, permissions, prompts, cancellation, and shutdown do not branch by brand.

UI/provider settings use the existing store; credentials use the OS credential store; thread/change metadata uses a Rust-owned local store selected during implementation. Local bundle reading remains network-free. Network begins only after an explicit install, auth, endpoint test, remote provider prompt, URL attachment, or update action.

The frontend keeps one bounded last-connection entry in webview storage: the kind (catalog, custom, or Studio model), its ID, a custom profile's launch mode, and a Studio profile's selected model — never credentials, prompts, or transcript content. Every successful explicit connect replaces it; an explicit disconnect that matches it removes it. At most once per app session, the open panel beside an active bundle replays that entry through the ordinary typed connect command, marks the resulting connection as restored so its first surface may resume the saved thread pointer, and falls back to the normal connect state on any failure. Restore is a continuation of the user's prior explicit connection, not a new autonomous launch path.

# ACP process host

Studio pins the official Rust SDK at `agent-client-protocol` 2.0.0 with schema artifact 1.5.0. Artifact versions describe the Rust API and generated schema; wire compatibility is negotiated separately. Studio requests ACP protocol v1 and rejects any response that selects another version — the SDK's 2.0 major bump changed its Rust API, not the wire schema, so the version an agent negotiates is unaffected by it.

The host starts custom and installed catalog agents only through typed connect commands. Each command requires one bundle root that the live Rust grant registry recognizes, and completes that canonical check before process creation. The worker and returned connection record retain the exact root. Session create, list, and load reject a different canonical root before sending an ACP request. Switching bundles therefore cannot repurpose an already-running external process; the panel omits it from another bundle's connection strip, while the catalog can still disconnect it. Returning to its bundle mounts a fresh conversation surface under the existing bundle-change reset rule. This binding supplies the immutable root used by platform confinement and mediated tools. A Standard process is not restricted by the binding itself. A custom profile supplies its stored absolute executable and argv. A catalog agent supplies a revalidated managed Node executable and package entry point. Both clear the child environment, then restore only their allowlisted values. The process receives piped stdin/stdout for JSON-RPC and a separate stderr reader. Initialization has a 15-second deadline and sends the Studio implementation name and version. The response is reduced to typed implementation, authentication, capability, and bundle-binding fields before crossing IPC; arbitrary agent metadata does not cross.

Every external ACP launch also receives a platform process-tree owner. Linux and macOS place the child in a new process group before `exec`; teardown sends `SIGKILL` to that group. Windows assigns the spawned child to a private Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; descendants inherit the job, and teardown terminates the job before closing its handle. If Studio cannot attach the owner, the direct child is killed and the connection fails. After a successful attachment, the launcher produces a closed scope record naming that platform mechanism and the selected launch profile. ACP initialization cannot return a connection without this record. Normal disconnect, removal, unexpected parent exit, initialization failure, task cancellation, and application shutdown all pass through this owner. Tree termination happens before Studio awaits stderr so a descendant cannot keep diagnostics open. An explicit direct-child kill and `kill_on_drop` remain fallbacks. Process-tree ownership prevents ordinary descendant leaks but grants no filesystem, credential, IPC, process-spawn, or network restriction by itself. Standard external ACP agents therefore remain ineligible for unattended writes; a Restricted offline profile must add and prove its operating-system boundary.

The connection result carries a Rust-produced security-scope record with launcher evidence, process containment, and one closed reusable profile. A profile reports its ID, effective mounts, writable roots, network policy, credential exposure, lifetime, stop conditions, and unattended eligibility. `studio-native-mediated-v1` exposes the active bundle only through bounded tools, keeps proposals in reviewed staging, sends a saved key only to the configured endpoint, and has no external process. `external-interactive-unrestricted-v1` reports host operating-system files, writes, network, and credentials, including its allowlisted launch environment; Studio's bundle tools and staged writes remain narrower than the process itself. `external-linux-restricted-offline-v1` reports read-only system runtime, exact agent executable, and read-only bundle mounts; private temporary writes; isolated networking; and launch-environment-only credential exposure. `external-windows-restricted-app-container-v1` reports the AppContainer runtime and Studio-mediated bundle access, private profile writes, isolated networking, and launch-environment-only credential exposure. All four profiles last for one connection and stop on disconnect, application exit, or host failure. Only the two verified Restricted offline profiles are unattended-eligible. Their grants expire after 30 minutes and still cannot Apply a staged revision.

An external record exists only after its selected command has spawned and the launcher has attached the process-tree owner. Restricted scope therefore cannot come from the saved mode, backend preflight, or agent metadata. The native record comes from the Studio provider host. The conversation toolbar renders this record instead of inferring scope from a frontend profile or protocol-version check. A restricted record proves either the Bubblewrap launch path with POSIX process-group attachment or the AppContainer launch path with Windows Job Object attachment; that live evidence alone exposes the expiring unattended staging option.

Authentication stays agent-owned. Studio reduces initialization to at most 16 bounded stable methods and sends only the selected advertised method ID through ACP `authenticate`; browser pages, subscription state, tokens, and API keys remain with the external agent. Authentication has a five-minute deadline and a retryable UI state. Rust rejects invented method IDs and blocks session creation until authentication succeeds. Connections without advertised methods start ready. The frontend records only the authenticated connection state so the panel can unlock the composer. ACP's client-owned terminal and environment-variable variants remain unstable and are not enabled.

Permission requests are deny by default. Rust accepts them only for a session with an active turn, exposes at most 16 advertised choices, and sends only the bounded tool-call ID, human title, choice ID, label, ACP choice kind, and whether exact-thread reuse is available to the webview. Raw tool input, output, content, locations, and extension metadata never cross IPC. The user may select only an ID the agent offered or cancel. Requests expire after five minutes and resolve as ACP `cancelled` when the turn, connection, profile, or app ends. A Studio-owned thread rule is available only when the request supplies a bounded title, declared tool kind, raw input, and locations whose streamed serialization fits 64 KiB. Rust hashes that exact tuple with SHA-256 and stores only the connection, session, fingerprint, and allow-or-reject direction in memory. Remembering accepts only an advertised `allow_once` or `reject_once` choice. A later exact fingerprint automatically selects only a currently advertised once-choice in the same direction; it never invents an option or upgrades to `allow_always`. Creating or loading the session clears its rules, and disconnect drops them. Agent-advertised `allow_always` and `reject_always` remain agent-owned choices and do not become Studio rules. Broader cross-session rules require a stable tool identity and visible scope that ACP v1 permission requests do not provide. Stderr retains at most the latest 64 KiB, removes control characters, and redacts inherited values before it can enter an error. Disconnect aborts the connection future and tears down the owned process tree. Removing a profile aborts every connection that uses it, and dropping the app-owned host state aborts all remaining trees. Fake in-process agents cover permission selection, exact-input reuse, and invalid-choice rejection alongside initialization, advertised capability/auth capture, timeout, bounded diagnostic redaction, and profile-wide shutdown.

After initialization, each connection becomes a small Rust-owned actor. Typed commands enter through a bounded channel instead of sharing the SDK connection across Tauri requests. Session creation canonicalizes an absolute bundle directory off the async runtime, rejects missing and non-directory paths, and sends that directory as ACP `cwd` with no additional roots. It has a separate 30-second deadline. Studio returns the stable connection ID, session ID, canonical bundle root, initial staged state, and a reduced session-configuration snapshot; arbitrary agent metadata does not cross IPC. The actor retains the session-to-root association for later prompt and tool scoping. A fake agent asserts the exact canonical root it receives.

Studio advertises ACP select and boolean session configuration support. New and loaded responses are reduced to bounded IDs, labels, descriptions, categories, groups, values, and current state before crossing IPC. The actor serializes changes through `session/set_config_option`, validates every requested ID, type, and value against its confirmed snapshot, replaces the complete snapshot from the response, and forwards bounded agent-initiated replacements. When an agent returns no modern configuration but does return legacy session modes, the actor projects one synthetic mode option for the frontend and translates its changes to `session/set_mode`. Any non-empty modern set wins, so one mode cannot appear twice. Current-mode notifications update only a legacy projection. Native Studio sessions publish the connected model through the same reduced option shape. The native host accepts only that advertised value and leaves unsupported mode and reasoning categories absent.

The panel renders one conversation instance for every active connection and hides rather than unmounts inactive instances. Selection is frontend-only; the connection registry, actor, session, turn, permission, staged tree, and cancellation boundary remain independent. Every frontend event listener rejects a mismatched connection or session ID. Per-instance generated DOM IDs keep labels and accessible regions from targeting a hidden conversation. This first parallel slice permits concurrent turns across distinct connections while preserving the one-active-turn rule within each session. Multiple conversations on one connection require a later extraction of thread state and do not follow from this layout.

Studio advertises ACP `fs/read_text_file` and `fs/write_text_file`. A read is accepted only for an active session and an absolute path whose canonical target remains under that session's canonical bundle root. Canonicalizing the target before the root check rejects `..` traversal and symbolic-link escape. The same case-insensitive built-in policy used for writes denies Git metadata, credential and secret paths, and packaged agent instructions before returning content or creating an explicit context link. Directories, missing files, non-UTF-8 content, zero-based line requests, and text above 1 MiB are rejected. Valid requests preserve line endings and apply ACP's 1-based `line` and maximum-line `limit` fields. Fake-agent tests cover the advertised capabilities and a ranged read, while boundary tests cover outside-root, sensitive, binary, and oversized files.

Sensitive-path protection is non-overridable and case-insensitive on every platform. It covers `.git`; common credential stores and secret directories; `.env` variants; private-key and credential file formats; `.agents`, `.claude`, and `.codex` content; and standard agent-instruction filenames. It applies before staging and rejects a reported ACP diff batch in full. Nearby knowledge paths such as `credentials.md` and `security/secrets.md` remain valid.

A write is deny-by-default: without the user's **Allow edits in this thread** grant, `fs/write_text_file` fails with an error naming the grant, and opening a bundle or approving a generic ACP permission never enables it. The grant is Rust-owned per-connection state keyed by session ID, set only through a typed command, never persisted, and revoked when a session is created or loaded, so a restored session always starts read-only. A granted write never reaches the filesystem: it lands in a bounded in-memory staged tree keyed by bundle-relative forward-slash path. Path reduction accepts an absolute Unicode path lexically under the canonical root in either its verbatim or Win32 spelling, rejects traversal, `.git` components, control characters, and over-1,024-character paths, and canonicalizes the deepest existing ancestor so a symbolic link on any existing prefix cannot escape the root. Staged files are capped at 1 MiB each, 64 files and 8 MiB per session; whether a write creates or modifies is decided against the real bundle once and kept stable. Reads overlay staged content so a granted agent observes its own writes, including files that do not exist on disk yet. Grant changes, staged writes, and discard commands emit one bounded staged-change snapshot event carrying relative paths, byte counts, and create/modify kinds; staged content itself does not cross event IPC. An explicit per-file review command reads at most one 1 MiB original, compares it with the staged text off the async runtime, and returns structured unified-diff hunks capped at 262,144 characters with a truncation flag. The response carries a SHA-256 revision over the path, kind, original text, and staged text. Hunk choices live in the Rust staging service and are keyed by that revision. Ordinary edits and new files default to selected. Enhance modifications separately record which hunks received an explicit Keep or Reject choice, and validation and Apply require the complete current diff to be reviewed. A typed selection command accepts only a reported hunk index and the exact revision; a later agent write clears the choices, while an original-file change makes them stale. Truncated diffs expose no mutable hunk choices and therefore cannot pass the Enhance review guard. A separate command rejects one staged file by its reported path without changing the grant. Validation clones the stage and hunk choices, copies at most 4,096 Markdown files and 32 MiB into a short-lived system-temp mirror without following symbolic links or ignored directories, overlays the selected outcome, and runs `okf_core::read_bundle` off the async runtime. Fully rejected created files remain absent. The response carries aggregate totals, at most 512 bounded issues, and a SHA-256 revision over every staged path, file revision, and selected outcome. It also projects at most 128 parsed concepts and 512 resolved links from that same mirror, with staged flags and full graph totals. This revision-bound projection carries no Markdown body text. Scoped cleanup removes the mirror, and the bundle is never written. Apply holds the session's staging lock, rebuilds the selected outcome, requires the exact validation revision, and reruns the validator. It rechecks path containment, refuses symbolic-link targets, and verifies modification bytes or creation absence before preparing same-directory transaction files. Each replacement rechecks its base immediately before rename. A normal failure restores prior files in reverse order, removes prepared files and empty directories, and leaves the stage intact. Success clears the stage but preserves the thread grant. The latest successful apply is stored outside the bundle as one versioned, size-bounded checkpoint keyed by a SHA-256 fingerprint of the canonical root. It contains only bundle-relative paths and the bounded before/after text needed for guarded restore. The app-data directory and file receive user-only modes on Unix and inherited user ACLs on Windows; the bundle keeps no hidden backup after persistence succeeds. Before changing the bundle, Studio also stores a bounded apply-intent record containing the exact transaction paths, the proposed checkpoint, and the previous checkpoint if one exists. The new checkpoint is the commit point. On restart, an intent with that checkpoint keeps the applied files and removes recorded artifacts; an intent without it restores every original and reinstates the previous checkpoint. If checkpoint persistence fails, the same recovery path rolls apply back and keeps the reviewed stage. Session creation or load validates checkpoint and intent versions, fingerprints, UUIDs, counts, sizes, path containment, duplicate paths, created-directory ancestry, and the exact same-directory artifact names before returning a read-only staged snapshot. Restore requires an empty stage, checks that the app-data record is still the expected checkpoint, repeats containment and symbolic-link checks, and compares every current file with its applied bytes before changing any path. A restore-intent record is durable before Studio moves applied files aside, recreates original modifications through synced same-directory files, and removes creations. An ordinary failure rolls the batch back and retains the checkpoint; an interruption makes the next session finish the requested restore and consume both records. Recovery accepts only absent, original, or applied content consistent with the intent. A different bundle or artifact value blocks recovery without overwriting it. Invalid intent records are quarantined. A later apply replaces the older checkpoint. Write grants and staged drafts remain connection-only.

Each new ACP session includes a standard stdio MCP descriptor, which every ACP agent must support. The descriptor starts the current Studio executable in `--okf-mcp-grant <record> <nonce>` mode with an absolute executable path and explicit argv. The descriptor carries no bundle path. Rust creates the bounded record for the already-authorized session root, gives it a 60-second expiry, and the helper atomically consumes it before parsing the bundle. Missing, mismatched, stale, and replayed grants fail. Settings can issue the same one-shot descriptor for another local agent only after an explicit action on the active Rust-authorized bundle. That mode parses the bundle once and speaks MCP over inherited stdin/stdout. Two tools expose the active capability catalog and one declared resource at a time. `okf_inventory` pages at most 200 filtered concept summaries and returns promoted bundle metadata, preserved root extensions, and counts. `okf_read` identifies a concept through its bundle-relative ID, pages at most 1,000 body lines, and caps serialized body text at 64 KiB. `okf_search` returns at most 50 scored metadata/snippet matches. `okf_sources` pages at most 200 deduplicated canonical resources and external citations, retains their referring concept IDs, and performs no fetch. `okf_traverse` is cycle-safe, capped at three breadth-first hops and 200 concepts, and preserves authored link direction. `okf_validate` pages at most 200 parser and conformance issues with severity totals. Filters, offsets, and every serialized string are bounded; outputs contain concept IDs rather than absolute paths. No write, shell, network, or arbitrary-file tool exists. This helper is mediation, not a sandbox: an already-unsandboxed external process retains its operating-system access.

Prompt context is an ordered list of bundle-relative file paths, capped at eight bounded entries. A searchable picker exposes the bundle inventory, prioritizes the concept open beside the panel, suppresses duplicates, and shows each chosen concept as a removable chip. Rust resolves every attachment against the session's canonical bundle root, rejects absolute paths, traversal, symbolic-link escape, directories, and missing files, then sends the file resource links in picker order before the unchanged user message. The webview never reads a concept body. An accepted turn clears the attachments; a rejected prompt leaves them available for correction or retry.

Reader selection context reuses the text-source boundary rather than the file-resource boundary. The user selects text in the rendered concept and opens the composer context menu. At trigger activation, the frontend verifies that every selection range starts and ends inside the current reader scope, extracts plain text, and rejects empty or over-65,536-character selections. It sends a bounded title, the text, `text/plain`, and a bundle-relative `<concept>.md#reader-selection` origin. No HTML, DOM reference, absolute path, or read grant enters prompt state. Rust applies the existing eight-source, per-source, and combined-content validation before constructing the labelled ACP text block. The removable chip and queued draft retain the captured snapshot; later selection changes do not alter it. Reader selections remain outside transcript export.

Pasted sources cross IPC as title and content pairs. A validation issue selected from the parsed bundle uses the same bounded text-source boundary with its severity and concept ID as visible provenance. It counts toward the shared eight-source limit and remains untrusted prompt evidence; attaching it grants no write or filesystem capability. Local sources enter through Rust-owned native file and folder pickers that accept `.pdf`, `.txt`, `.md`, `.markdown`, `.html`, `.htm`, `.csv`, `.json`, `.yaml`, and `.yml`. YAML is accepted only when it is an OpenAPI document. The file picker reads only the selected paths. The folder picker walks the selected directory without following symbolic links, inspects at most 4,096 entries across eight levels, ignores unsupported files, and sorts supported files by relative path. It fails when the supported set cannot fit in the remaining source tray instead of dropping files. The webview receives the filename or folder-relative path as a bounded origin label and a closed-set media type, never an absolute path or reusable filesystem grant. HTML is transported as text and never enters a webview HTML sink.

Every native intake path delegates to the versioned [source-adapter contract](../features/source-adapters.md). Its receipt records schema, adapter, discovery mode, origin, media type, source fingerprint, normalized-evidence fingerprint, refresh fingerprint, untrusted status, and partial-success diagnostics. Rust recomputes all fingerprints and rejects a mismatched origin, media type, adapter version, trust label, evidence body, or refresh contract at prompt submission. The source inventory exposes those fields before send. The labelled ACP or native context block repeats the complete adapter identity before the normalized evidence. Instructions found in any source remain inert data.

Image intake is available only when the connected agent advertises ACP image prompt support. A Rust-owned picker accepts PNG, JPEG, and WebP, verifies each file's signature instead of trusting its extension, and caps one image at 8 MiB and all attached images at 16 MiB. The webview receives base64 bytes, the filename, media type, and original-byte SHA-256 only after explicit selection. Rust decodes and revalidates the size and digest on prompt submission. The actor rejects image blocks for an agent without the capability even if a webview request is forged. Studio does not decode, preview, OCR, or persist the image.

URL sources enter through a separate Rust-owned HTTPS fetch command. It disables environment proxies, permits at most three HTTPS redirects, and applies the same URL and DNS checks to every hop. Literal and resolved private, loopback, link-local, multicast, documentation, and other special-use addresses are rejected; a mixed DNS answer is rejected in full. The response must declare plain text, Markdown, HTML, CSV, JSON, or a JSON suffix media type. Studio caps the decompressed body at 256 KiB, stores the final fragment-free URL as provenance, and hashes the original response bytes. Remote PDFs, images, YAML, scripts, linked assets, and page subrequests are not fetched.

CSV sources are parsed locally with `csv` 1.4 in strict-width mode. Studio labels columns by position, converts quoted commas and multiline cells without losing their value boundaries, and emits Markdown tables in exact 100-row ranges. Malformed records and normalized output above 262,144 characters fail. The ACP provenance block carries SHA-256 of both the original CSV bytes and the normalized content sent to the agent.

JSON sources are parsed locally into a deterministic structural table. Every object, array, and scalar receives an RFC 6901 JSON Pointer. Object keys sort lexically, array indices stay in source order, and tables use exact 100-node ranges. Studio caps one document at 16,384 nodes and the existing 262,144-character normalized-output limit. Malformed input fails. The provenance block carries SHA-256 of the original JSON bytes and normalized content.

Before generic JSON normalization, Rust recognizes OpenAPI, dbt manifest, and BigQuery metadata export shapes. OpenAPI JSON and YAML normalize to the same sorted operation inventory and evidence fingerprint. dbt inventories nodes and sources with relations and dependency counts. BigQuery inventories datasets and tables with field counts. Missing operation IDs, empty manifests, and absent table schemas remain bounded warnings rather than false success. Malformed structured exports fail with their source title and parser or contract reason. These are export adapters only; Studio does not authenticate to the source services.

PDF extraction uses `pdf-extract` 0.12 and its `lopdf` 0.42 parser in a separate invocation of the current Studio executable. The parent passes the selected path as JSON over stdin, not argv, then caps stdout at 320 KiB, diagnostics at 4 KiB, and runtime at 15 seconds. The child caps input at 16 MiB and 256 pages, catches parser unwinds, rejects encryption and incomplete page extraction, and emits page-labelled Markdown. Image-only PDFs fail with an OCR-specific recovery message. Partly empty documents carry a warning. A parser crash or timeout terminates the helper rather than the desktop host.

Rust accepts at most eight sources, rejects controls in titles and origins and empty text content, caps titles at 256 characters, origins at 2,048 characters, each extracted body at 262,144 characters, all bodies at 524,288 characters, and the selected raw text files at 32 MiB. It accepts only supported media types and valid lowercase SHA-256 values. Text sources become labelled ACP text blocks with provenance and a digest of the exact submitted content. An image becomes a provenance text block followed by an ACP image block. Source attachments grant no later filesystem access and do not modify the bundle. Only the explicit URL mode performs a bounded network request. The first-turn client notice marks every source as untrusted knowledge.

Prompt submission accepts non-empty text capped at 128 KiB and returns a stable turn ID as soon as the actor accepts it. One turn may run per session. The frontend treats session creation and prompt acceptance as a waiting state. It adds the user message to the transcript and clears the composer and attachments only after acceptance. That first acceptance also derives a bounded plain-text thread title unless the user already supplied one. A pre-acceptance failure keeps the default title, editable prompt, and attachments in place and offers an explicit retry, so the transcript never claims that an unaccepted turn ran. While a turn is active, the frontend may retain one in-memory follow-up snapshot containing bounded prompt text, concept paths, and sources. It is visible, editable, removable, and excluded from the transcript. A terminal event dequeues it through the same prompt boundary. Rejection restores the snapshot to the composer; acceptance clears it and starts the next live turn. Rust never accepts concurrent turns and does not own or persist this queue. For each accepted prompt, the frontend also retains its already-bounded draft until the turn completes. A failure exposes a retry action while the same session is idle. Retry sends the saved draft through the ordinary prompt boundary as a new turn and keeps the failed output intact. A rejected retry stays available with its error; acceptance removes the old action. Non-failure stop reasons and history restore discard the snapshot. Prompt work runs in a child task so the actor can process cancellation concurrently; disconnect aborts the task set. `session/update` notifications are reduced to text chunks, structured plans, tool lifecycle fields, or usage for the matching active turn. Text chunks drop arbitrary metadata, strip controls, and are capped at 64 KiB. A plan carries at most 64 entries; each status and priority is reduced to a closed vocabulary and each control-stripped task is capped at 1,024 characters. A tool event carries only a control-stripped ID and title capped at 512 characters, closed kind and status values, and an optional replacement location list. Location reduction looks up the canonical root for the notification's session, then accepts at most eight absolute paths whose components remain lexically under that root. It rejects relative paths, `.` or `..`, the root itself, non-Unicode or control-bearing components, paths above 1,024 characters, and duplicate path-line pairs. Accepted paths cross IPC with forward slashes and optional positive line numbers. Files need not exist because ACP may report a prospective edit or deleted path. Symlinks receive no special access because a location remains metadata and can only select the ordinary reader when its reduced path exactly matches an active-bundle concept. Rust still drops tool arguments, output, content, absolute paths, and extension metadata. A usage event carries token counts clamped to `Number.MAX_SAFE_INTEGER` and an optional cumulative cost only when its amount is finite, non-negative, no more than one trillion units, and its currency is three ASCII letters. ACP metadata does not cross. The frontend replaces matching plan and tool cards rather than appending duplicate updates, merges absent tool fields, replaces or clears an advertised location list, and replaces one session usage value in the composer footer. Early plan and tool updates are inserted after their accepted user message. Turn cancellation or failure closes any still-running tool card locally. Completion reports a closed stop-reason vocabulary; failures carry the existing capped diagnostic message. The transcript renders cancellation, refusal, limits, unknown stops, and failures as labelled turn-status records rather than agent-authored messages. Usage and locations remain ephemeral and excluded from export. Cancellation sends ACP `session/cancel` only when connection, session, and turn IDs match the active turn, then waits for the agent's `cancelled` stop reason. Rust fake-agent tests cover plan and tool replacement, location and usage reduction, field bounds, raw-field exclusion, text streaming, successful completion, and cooperative cancellation. Frontend mock coverage adds pre-acceptance retry, accepted-turn retry, queued-start recovery, and failure after partial output.

ACP `available_commands_update` is handled outside active-turn reduction because it is a complete session snapshot. Rust accepts at most 64 unique command names, restricts names to 64 ASCII alphanumeric, hyphen, or underscore characters, strips controls from descriptions, caps them at 512 characters, and drops metadata and input schemas. The frontend matches only exact `compact`, `summarize`, or `summary` names for context recovery. Invocation remains an ordinary `session/prompt` containing `/<name>`, so the agent owns both the operation and its result. The accepted command appears as a user turn; a successful agent response is marked as a context summary and remains in Markdown export. Without such a command, Studio creates another mounted thread and preloads, but does not send, a 16 KiB carry draft made from at most the four newest user or agent text entries. The draft explicitly excludes files, attached sources, permissions, grants, staged state, and any claim of checkpoint or agent-state rewind.

The current in-memory thread can be exported as Markdown after its first accepted message. Its bounded title becomes the document heading and safe suggested filename. The document identifies the bundle and agent, quotes user messages, writes the latest structured plan for each turn as a task list, labels tool titles and final states, preserves agent Markdown, and labels lifecycle records as turn status. Before a guided Deep research export crosses IPC, the frontend checks agent messages for a Markdown `Sources` section with at least one list item containing a Markdown link, public URL, or bundle-relative `.md` path and a non-empty `Inferences` section. A guided dataset-change export instead requires a non-empty `Change Plan` list and an `Affected Concepts` list containing a bundle-relative `.md` path. Missing structure blocks the save dialog with an actionable error. These predicates inspect only agent-authored Markdown and do not claim to validate evidence quality, proposal completeness, or whether a path exists. The dataset predicate is the required precondition for later reviewed-write entry points. Export is unavailable while a turn or save is active. Rust accepts at most 2 MiB, opens the native save dialog, writes only the explicitly selected `.md` destination, and returns the filename rather than its absolute path. Cancelling changes nothing; a write failure stays visible and retryable. Export does not persist the transcript and never includes raw permission arguments, tool arguments or output, tool locations, credentials, or agent diagnostics that were already excluded from frontend state.

The first prompt in each session carries the resources selected from the same manifest used by Studio Agent. If the agent advertises ACP embedded-context support, Studio sends each as a Markdown resource with a versioned `okf-studio://` URI. The compatibility path uses bounded labelled text content, which every ACP agent must accept. Both paths include a `file:` resource link to the canonical bundle-root `index.md`, a client-context notice that treats bundle files as untrusted knowledge, and the unchanged user text as the final content block. Context is marked attached only after a successful prompt response, so a failed first turn retries it; later turns avoid paying the context cost again.

Every accepted turn returns a compact capability receipt instead of copying resource bodies into the transcript. It records capability ID and version, manifest digest, full or degraded support, delivery as native catalog, ACP embedded resources, ACP text fallback, or retained session context, the delivered resource IDs, and native resource loads observed during the turn. The receipt type includes unavailable support for future task-specific capabilities. The external MCP server can deliver a generic-chat resource, but ACP does not provide Studio with an attested capability-use event. Studio therefore records the shared client-context delivery and leaves the agent's tool card or statement as provider-reported activity, not proof of compliance.

The capability build reads only `.agents/skills/okf/`, rejects paths outside that directory, and fails before Rust compilation on a changed SHA-256 digest, duplicate ID, invalid risk class, unsupported media type, missing file, or per-resource and total size overflow. Runtime parsing repeats the closed ID, version, tool, artifact, path, media-type, hash, and size checks. Build verification and runtime selection therefore use one canonical resource set without trusting webview input or provider output.

ACP v1 tool-call content is reduced before the lifecycle event crosses IPC. Standard content, terminals, raw patch material, and agent-provided base text remain private to Rust. A tool-call or replacement update containing full-text `Diff` items becomes one atomic compare-and-stage request of at most 64 files. It uses the same live-session grant, root, path, file-count, and byte limits as `fs/write_text_file`. Each `oldText` must equal the current staged overlay or bounded UTF-8 disk text; `None` requires an absent file. A mismatch, including a file already changed directly by a Standard external process, rejects the entire report. An identical report for content already in staging is idempotent and preserves hunk choices. An accepted batch emits the ordinary staged-change snapshot. The reduced tool event carries only `staged`, `not-staged`, or no change state. This reports the mediation result without treating ACP's completed status as an applied Studio change. Standard external connections remain interactive because the process can bypass client filesystem requests. Verified Restricted offline connections may stage unattended because the operating-system boundary prevents direct bundle writes.

# IPC

Tool lifecycle updates carry only a bounded change-state label after Rust has reduced any ACP diff content into staging; the content itself never crosses IPC.

Implemented commands cover custom and catalog-agent connect, disconnect, authentication, session creation, text prompts, turn cancellation, permission responses, local-endpoint profile persistence and probing, explicit transcript export, staged-file diff review, revision-bound hunk selection, staged-file rejection, isolated staged-tree validation, exact-revision edit apply, fresh-bundle creation, and checkpoint restore with stable connection, session, turn, and request IDs; Rust rejects a second active connection for the same source. Typed events report connection termination, reduced turn updates, requested/resolved permission state, and staged-change snapshots. Session creation and load also return the initial read-only staged snapshot so a persisted Restore action cannot race an event before the frontend knows the session. The IPC module retains active connection identity and one app-lifetime connection listener so catalog remounts do not lose live process state. Failure messages remove controls and are capped before IPC. Install progress remains event-based. Stable IDs let the frontend reject late updates without reopening completed requests.
