# What it does

The center of the workspace renders the active bundle as an interactive **force-directed graph**: one node per concept, one edge per cross-link. The relationship structure is implicit in the markdown links. The graph makes it visible and navigable. The graph is the default of the pane's four [visualization views](viz-views.md). A switcher in the pane's toolbar swaps it for a treemap, sunburst, or circle packing of the same bundle.

# Visual encoding

- **Node = concept.** Color comes from one of two modes (a Controls toggle). The first colors by `type` via the deterministic palette, the default-ish semantic coloring, and the legend doubles as a [type filter](search-and-filter.md). The second colors by **detected cluster**. Community detection with **Louvain** groups densely-interlinked concepts and gives each community one color, so emergent clusters read at a glance.
- **Node size** scales with degree (how connected a concept is), so hubs stand out.
- **Edge = cross-link** between concepts. Each edge draws in its **source (citing) node's color** (Gephi's convention, following the active color mode). Hub fans and cluster membership then read from the wiring as well as the dots. Selecting or hovering a node accents its incident edges. It also adds an **arrowhead at each cited end**, and reciprocal links show both. Citation direction then appears exactly where the user looks, while the overview stays clean. A richly cross-linked bundle is dense enough that drawing *every* link reads as a hairball. So by default the graph draws a **structural backbone**, each concept's most significant edges, rather than all of them. A Controls *Links* setting trades readability for completeness. See [Implementation notes](#implementation-notes).
- **Label** shows the concept `title`, **sized by the node's importance** (hubs get larger labels). Labels are **level-of-detail** in the dataviz sense. Each node's reveal threshold scales with its size, so zooming out sheds leaf labels first and keeps the hubs as a labeled map. The graph **collision-culls overlapping labels by priority** (selection/hover context first, then bigger nodes) rather than smearing them. It always labels the selected node, its neighbors, and the hovered node.

# Interaction

- Pan (drag background), zoom (wheel), drag nodes to reposition, **click** to open a concept, **Fit** to reframe. [Keyboard shortcuts](../ux/keyboard-shortcuts.md) cover all of it too (`+`/`−` zoom, `F` fits). A settling layout **stays framed while it organizes**, both for a brand-new bloom from the spawn ring and for a focus/isolate/explore re-settle. Rather than reframe once and let the graph drift (or sprawl off-screen) until a late fit, the view **eases toward the fit every frame**. It glides in on entry and follows the spread, always centered and fully visible as the graph **assembles in view**. The moment you pan, zoom, or drag, auto-framing yields to you and never fights your view.
- **Double-click a node to explore**, the expand-on-click interaction at the core of [Neo4j Bloom](../proposals/lineage-and-traversal.md). The graph restricts to that concept and its neighbors. Each further double-click **pulls in another node's neighbors**. You build a neighborhood outward one hop at a time, instead of starting from the whole hairball. Cached positions mean the newly-revealed nodes animate in from where they were rather than re-spawning. An `Exploring N · exit` chip shows the set size and returns to the full graph. **Overview**/**Focus** also exit it. This is the incremental, additive complement to Focus mode's fixed-depth ego view.
- **Fit and the zoom buttons glide** rather than teleport. A short ease-out moves the point under the viewport center linearly and interpolates scale geometrically. The step then reads as movement through the graph. Direct input (wheel, pan) interrupts the glide and takes over. **Reduce motion** ([settings](../ux/settings.md)) makes every transition instant.
- Click a node to open it in the [Concept Reader](concept-reader.md) and recenter on it.
- With a node selected, **Agent** opens [Native OKF Tasks](native-okf-tasks.md) with that graph object as the explicit starting scope. Change impact leads the task choices. If you cancel the launcher, the graph and reader selection remain unchanged.
- **Selecting** a node keeps the whole graph bright, rings that node, and accents its links. The open concept's connections stand out without hiding the rest. A **hover** dims everything except the node and its neighbors, to trace one neighborhood at a time. Either way structure stays readable in a dense graph.
- Hidden types (toggled in the legend) drop out of the layout, and [search](search-and-filter.md) dims non-matches. Filtering by [typed relationship](typed-relationships.md) lives in [Lineage](lineage.md), not in the graph chrome, so every visualization shares the same toolbar.

# Controls

A collapsible controls panel (top-left of the graph, in the spirit of Obsidian's graph view) tunes the view without leaving it. Every control sits under a **titled section with a one-line description** and uses a **plain-language label**. Sliders also show their **live value** and a short hint of what they do, so the panel *teaches* rather than only labels. The panel scrolls when it outgrows the viewport.

- **Renderer**: *Canvas* (the default) or *GPU* (WebGL, for very large graphs). The canvas renderer carries the full control set, level-of-detail labels, and defect markers. See [Implementation notes](#implementation-notes).
- **Connections**: the [link density](#visual-encoding) (*Key* / *Balanced* / *All*): how many edges the graph draws, from each concept's strongest few to every cross-link. A live hint names what the current choice does.
- **Color**: color nodes by detected **cluster** (Louvain community) or by concept **type**.
- **Appearance**: *node size*, *link thickness*, *link opacity*, and *label visibility* (how early titles appear as you zoom in).
- **Layout**: fine-tune the forces in plain terms, namely *spacing* (how hard nodes push apart), *link length*, *link pull*, *gravity*, and *cluster pull*. The *cluster pull* control sets how strongly each detected community gathers around its own center **and pushes apart from other communities**. Adjusting one control gently reheats the layout so it re-settles.

A **Reset to defaults** restores the tuned starting point. The graph **auto-fits** the viewport once a fresh layout settles. A **collision** pass keeps nodes from overlapping, so clusters read as distinct blobs rather than a tangle.

# Focus mode

By default the graph shows a **focused neighborhood** of the selected concept rather than the whole bundle. The neighborhood is that concept plus its neighbors out to an adjustable **depth** (1–3 hops over links and backlinks). It answers "what relates to *this*?" instead of presenting a hairball. An **Overview / Focus** toggle switches to the full graph, and Overview is the default until you select a concept. A depth stepper sets the hop count. Toggling reuses cached node positions so the layout animates rather than jumps.

Mode and depth are **one control on one surface**, divided by a hairline rather than split into two floating pills. The depth stepper only exists in Focus. As a separate pill it changed the toolbar's silhouette per mode and wrapped into a staircase on a narrow pane. With no concept selected the graph cannot focus. The "Select a concept to focus" hint then sits beneath the control as quiet canvas text with a background halo. It is not a third pill competing with the buttons above it.

# Surfacing defects

The graph makes conformance problems visible instead of hiding them. A concept with no links in or out is an **orphan**, and it gets a marked ring. A concept with **broken links** gets a warning marker. A count chip (`N orphans · M broken`) isolates that set on click. This stays [tolerant](validation.md): the graph surfaces defects, never rejects them, and uses the same severity language as [Validation](validation.md).

# Implementation notes

- The [Rust core](../architecture/okf-parsing.md) computes the graph data (nodes, edges, backlinks) from the [data model](../architecture/data-model.md) and hands it to the frontend as JSON.
- The default layout/render runs in the frontend on a **canvas**, and it keeps positions and the simulation out of React's render path. Repulsion uses a **Barnes–Hut quad-tree** (O(n log n)), **weighted by node degree** as a ForceAtlas2-style body mass. Hubs and dense clusters therefore claim more space and separate emergently. A **LinLog link attraction** (a gentle logarithmic pull that doesn't tighten with distance) keeps connected clusters from collapsing into a central tangle. Together the two give a neat, untangled distribution. A **collision** pass prevents overlap, so the view scales from tens to thousands of nodes. A cooling schedule settles the layout and then the loop idles. On top of the emergent structure, a **cluster force** makes the geometry *agree with* the detected communities that also drive the default coloring. It runs in two passes. The **gravity** pass (cosmos.gl's point-clustering idea) pulls each node gently toward its **Louvain community's centroid** for tighter blobs. The **separation** pass gives each community a soft circular bubble (radius ∝ √members) and pushes overlapping bubbles apart. Distinct communities then settle into distinct regions instead of interleaving. That is the clean auto-clustering that otherwise needed a manual wiggle. Both passes fade as the layout cools and ride the single *Cluster pull* control. See [Performance & Scale](../architecture/performance.md) for the full strategy and the [fast principle](../product/principles.md) it serves.
- **Interaction stays cheap regardless of size.** A trackpad zoom fires a flood of wheel events. A synchronous redraw on each one backs up the main thread and reads as a freeze, worst on the slower WebKitGTK webview. So wheel and pan **coalesce to at most one redraw per animation frame**. **Every draw pass culls to the visible viewport**: edges, nodes, broken-link markers, and the priciest one, labels (O(labels²) collision-culling plus text layout). The canvas skips off-screen nodes and trivial-rejects off-screen edges by Cohen–Sutherland region codes. That rejection is exact, so the canvas never drops a segment that crosses the viewport. Zooming into one cluster of a large graph therefore draws only the handful of on-screen items rather than the whole bundle. The canvas also uses an **opaque context** (`alpha: false`, and it paints the theme background itself). That skips per-pixel alpha compositing with the page, a win on WebKitGTK. Every frame also **batches its draws by color**: one `fill`/`stroke` per node color and per edge color instead of one per node/edge. A graph of hundreds of nodes then issues a handful of canvas calls rather than thousands. Those calls are the dominant cost when the whole graph is on screen. Node batching is exact, because the collision pass guarantees nodes never overlap. Edges composite their opacity once per color group, a hair cleaner than the old per-segment buildup. Two more costs scale with the *viewport* rather than the node count. That is why a large or maximized window lagged where a small one didn't. The first is the per-frame pixel fill (`width × height × devicePixelRatio²` pixels painted every frame). The second is the label pass: a collision cull plus a `fillText` per on-screen label. Both are slow on WebKitGTK, and both grow as a bigger window reveals more labels. So the canvas **caps its backing resolution to a pixel budget**. A large window renders at a slightly reduced device-pixel ratio, bounded by `MAX_DPR` and `√(budget / area)`. The compositor then scales it up, the standard "smaller canvas scaled up" HiDPI technique. And **while the layout settles only the hub anchors stay labelled**: the largest nodes plus the always-shown selection/hover set, drawn without the collision cull. The fine leaf labels and the full cull wait for the settled landing frame. Detail fills in as the graph lands rather than every label blinking, and the per-frame cost stays bounded regardless of window size. Together these keep pan, zoom, and hover smooth from tens of nodes to a dense bundle, and independent of window size.
- A bundle's cross-links are deliberately rich (good for navigation), which makes the raw graph **dense**. Our docs bundle averages ~14 edges per node, and no force layout can untangle a graph that near-complete. So the view draws a **backbone** rather than every edge. It weights each edge by how much that edge reveals structure (mutual links, shared neighborhoods, shared tags). Each concept keeps only its strongest few, a weighted **k-nearest-neighbor** graph. A **maximum spanning forest** goes over the top, so pruning never disconnects the graph. This is the established *edge-filtering / backbone-extraction* approach for dense networks. We use weighted top-k rather than the disparity filter ([Serrano et al., 2009](https://www.pnas.org/doi/10.1073/pnas.0808904106)), because our near-binary edge weights make that filter degenerate. The *Links* control (Key / Balanced / All) sets how many edges per concept survive. The graph still computes communities and focus neighborhoods on the **full** link graph. Cluster colors and "what relates to this" stay complete regardless of the density setting.
- An optional **GPU renderer** (cosmos.gl) runs the same force model entirely on the graphics card via WebGL. It scales to graphs far larger than the canvas path comfortably handles. It keeps community coloring, degree-scaled node sizes, click-to-open, hover highlight, [focus mode](#focus-mode), Fit, and an HTML label overlay for the selected and hovered concepts. It **loads on demand**, so its WebGL bundle downloads only when you select it and the default path stays lean. If WebGL is unavailable in the host webview, it **degrades gracefully to the canvas renderer**. The canvas renderer stays the default and the more fully-featured of the two.
- Broken cross-links simply do not produce edges. The graph [tolerates](validation.md) them. They are not errors.
